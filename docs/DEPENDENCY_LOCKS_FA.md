# قفل تکرارپذیر وابستگی‌ها

هدف Kira ویندوز ۱۱ با معماری x86-64 و CPython نسخه‌های ۳.۱۱ و ۳.۱۲ است. فایل‌های requirements بازه‌های سازگاری را تعریف می‌کنند و Lockهای تولیدشده، خروجی کامل Resolver شامل نسخه‌های دقیق و هش SHA-256 را برای هر گروه و هر هدف Python ثبت می‌کنند.

## مرز وابستگی‌های Core و اختیاری

- `requirements.txt` وابستگی‌های اجباری هستهٔ برنامه را تعریف می‌کند.
- فایل‌های `requirements-*.txt` قابلیت‌های اختیاری و مستقل را تعریف می‌کنند.
- `requirements-dev.txt` فقط ابزارهای توسعه را نگه می‌دارد.
- فایل‌های `constraints.txt` و `constraints-voice.txt` تصمیم‌های سازگاری مشترک گروه‌های مرتبط را اعمال می‌کنند.

ابتدا Lock هسته برای هر نسخهٔ Python حل می‌شود. سپس هر Lock اختیاری با همان Lock هسته به‌عنوان Constraint اضافی تولید می‌شود؛ بنابراین یک قابلیت اختیاری نمی‌تواند بی‌صدا نسخهٔ وابستگی Core را تغییر دهد. گروه‌های اختیاری مستقل Resolve می‌شوند: تعارض یا در دسترس نبودن بسته در یک گروه فقط Lock همان قابلیت را حذف می‌کند و مانع تولید یا نصب Core نمی‌شود. نصب‌کننده می‌تواند گروه اختیاری بدون Lock را از مسیر عادی Resolver بررسی کند و در صورت شکست، فقط همان قابلیت را ناموفق اعلام کند.

وابستگی Core به‌صورت عمدی `google-genai<3` باقی مانده و `constraints.txt` در حال حاضر نسخهٔ سازگار شاخهٔ ۲.x را محدود می‌کند. Gemini Live از همین وابستگی Core، ماژول `google.genai` را دریافت می‌کند و به بسته‌های گفتار محلی اختیاری وابسته نیست. موتور Kitten نیز برای جلوگیری از نصب درخت اختیاری PyTorch، گروهی مستقل با `--no-deps` باقی می‌ماند.

## تولید یا به‌روزرسانی Lockها

راه‌اندازی عادی، پیش از نصب وابستگی‌ها ابزار تولید Lock را اجرا می‌کند. توسعه‌دهندگان می‌توانند از ریشهٔ مخزن و با دسترسی به مخزن بسته‌های Python اجرا کنند:

```powershell
py -3.12 -m pip install --upgrade uv
py -3.12 scripts/generate_dependency_locks.py

# فقط برای ارتقای عمدی وابستگی‌ها:
py -3.12 scripts/generate_dependency_locks.py --refresh --snapshot-cutoff 2026-12-01T00:00:00Z
```

هدف Resolver برابر `x86_64-pc-windows-msvc` است و خروجی در مسیرهای `dependency-locks/windows-x86_64/python311/` و `python312/` قرار می‌گیرد. با `--python-versions 3.11` یا `--python-versions 3.12` می‌توان فقط یک هدف را بازتولید کرد. آینهٔ معتبر PEP 503 از طریق `--index-url` یا متغیر `KIRA_PYPI_INDEX` قابل انتخاب است؛ اطلاعات ورود نباید Commit شوند.

رفتار Resolver صریح است: انتخاب بالاترین نسخهٔ سازگار تا یک تاریخ انتشار ثابت، تولید Hash، نادیده‌گرفتن تنظیمات محلی uv و حذف URL مخزن از Lock. ابزار Fingerprint ورودی‌ها را کنار Lockها ذخیره می‌کند. نصب عادی Lock معتبر و همسان را دوباره استفاده می‌کند و وابستگی‌های پروژه را بی‌دلیل ارتقا نمی‌دهد. برای ارتقای عمدی، دستور را با `--refresh` اجرا و تاریخ `--snapshot-cutoff` را به تاریخ انتشار موردنظر جلو ببرید. تمام خروجی ابتدا در فضای موقت ساخته می‌شود. شکست Resolve یا اعتبارسنجی Core، Lockهای قبلی را حفظ می‌کند. شکست گروه اختیاری جداگانه گزارش می‌شود و مانع Core نیست.

هر Pin باید یکتا باشد و هش SHA-256 مستقل داشته باشد. Fingerprint یکسان باعث استفادهٔ مجدد از Lock در نصب عادی می‌شود؛ Lock اختیاری ناموجود تا زمان تغییر ورودی‌ها یا Refresh عمدی، ناموجود باقی می‌ماند. نصب‌کننده در صورت وجود Lock متناسب با Windows x64 و نسخهٔ Python، آن را با `--require-hashes` به pip می‌دهد. اگر Lock اختیاری موجود نباشد، نصب‌کننده فهرست Pinهای سادهٔ Core را نیز به Resolver همان گروه اضافه می‌کند و سپس پیش‌بررسی و Rollback را اجرا می‌کند؛ بنابراین مسیر جایگزین نیز نسخه‌های انتخاب‌شدهٔ Core را تغییر نمی‌دهد.

پوشهٔ `dependency-locks/` خروجی محلی ساخت است و عمداً در Git نادیده گرفته می‌شود. نسخه‌ها و Hashها را دستی تغییر ندهید؛ فایل‌های منبع requirements/constraints را اصلاح و Lockها را دوباره تولید کنید. این Lockها مختص هدف تعریف‌شده‌اند؛ سیستم‌عامل، معماری یا نسخهٔ Python دیگر به هدف Resolver مستقل نیاز دارد.
