# Computer Awareness و Tool System (مرحله‌ی ۱)

> برنامه‌ریزی چندمرحله‌ای، اجرای خودکار و مدیریت وظایف روی همین زیرساخت اضافه شده است: `docs/AGENT_FA.md`.

Kira حالا می‌تواند اطلاعات زنده‌ی ویندوز را بخواند و ابزارهای کنترل‌شده را اجرا کند. هیچ Shell آزادی در اختیار مدل نیست.

## چطور کار می‌کند
1. پیام تو بررسی می‌شود (بدون تماس با مدل). اگر درباره‌ی این کامپیوتر باشد (ساعت، RAM، فایل، باز کردن برنامه...) فهرست کوتاهِ ابزارهای مربوط به همان موضوع به Prompt اضافه می‌شود؛ در گفتگوی عادی **هیچ چیزی اضافه نمی‌شود** و به Context Window فشاری نمی‌آید.
2. مدل اگر ابزار لازم داشت، فقط یک بلوک می‌نویسد: `<kira_tool>{"tool":"get_datetime","args":{}}</kira_tool>` (کاربر این متن را نمی‌بیند).
3. برنامه ابزار را اجرا می‌کند و **نتیجه‌ی واقعی** را به مدل برمی‌گرداند؛ مدل جواب نهایی را با لحن همیشگی Kira می‌نویسد. چند ابزار پشت سر هم (تا ۴ مرحله) ممکن است.
4. روش متنی با همه‌ی Providerها و مدل‌های محلی کار می‌کند (نیازی به Function Calling نیست). فراخوانی تکراریِ یکسان در یک پیام دوباره اجرا نمی‌شود. اگر ابزار شکست بخورد، خطای واقعی به مدل و کاربر می‌رسد. اگر مدل بعد از اجرای ابزار از کار بیفتد، نتیجه‌ی واقعی ابزار به خودت نشان داده می‌شود.

## مسیر سریع قطعی (Fast Path)

برای فرمان‌های یک‌مرحله‌ای و کاملاً مشخص، Kira پیش از تماس با مدل از parser قطعی استفاده می‌کند. در صورت تطبیق دقیق، فراخوانی مستقیم ابزار انجام می‌شود و رفت‌وبرگشت مدل حذف می‌شود. موارد پشتیبانی‌شده شامل ساعت/تاریخ، بلوتوث، صدای سیستم، بازکردن برنامه، مشخصات سیستم، مصرف RAM/CPU/GPU/باتری، فضای دیسک، وضعیت شبکه و IP محلی، فهرست برنامه‌های باز و پنجره‌ی فعال است.

این مسیر فقط یک میان‌بر برای تشخیص درخواست است؛ اجرای ابزار همچنان از **ToolRegistry** و تمام کنترل‌های موجود عبور می‌کند: حالت ابزارها، سطح دسترسی، Access Manager و محدودیت Competitive Safe. عملیات حساس، ابزارهای خارجی، متن چنددرخواستی و عبارت‌های مبهم وارد Fast Path نمی‌شوند و به مسیر عادی مدل برمی‌گردند. parser نیز درک معنایی عمومی نیست؛ فقط الگوهای دقیق و پُراطمینان را می‌پذیرد.


### مرزبندی و وضعیت تکمیل Fast Path

Fast Path پنج مرحله‌ی مشخص دارد:

1. **Parser قطعی:** فقط یک درخواست کوتاه، تک‌مرحله‌ای و پُراطمینان را به نام ابزار و آرگومان تبدیل می‌کند. اگر تطبیق دقیق نباشد، خروجی parser برابر None است.
2. **گسترش پوشش فرمان‌های محدود:** پرس‌وجوهای خواندنی سیستم (مشخصات، مصرف منابع، دیسک، شبکه و پنجره‌های باز) به allow-list اضافه شده‌اند؛ این کار به معنی پشتیبانی از دستورهای آزاد یا زنجیره‌ای نیست.
3. **ایمن‌سازی Dispatch:** تصمیم پیچیده یا ادامه‌ی Task در Planner بر Fast Path اولویت دارد. ابزار باید در Registry وجود داشته باشد، داخلی و غیرحساس باشد و دسته‌بندی parser با ابزار و برنامه‌ی موجود منطبق بماند.
4. **آزمون مرز اجرای واقعی:** تست‌ها باید علاوه بر parser، مسیر ToolAgent → ToolRegistry را پوشش دهند؛ از جمله تغییر tools_mode یا فعال‌شدن Competitive Safe پس از برنامه‌ریزی و جلوگیری از اجرای تکراری در یک نوبت.
5. **مستندسازی و پذیرش عملیاتی:** قرارداد dispatch، مسیر اجرای امن، دستور تست و چک‌لیست آزمون Windows ثبت شده‌اند. تکمیل مستندات به‌تنهایی تأیید runtime محسوب نمی‌شود.

**قاعده‌ی قطعی:** Fast Path ابزار جداگانه‌ای برای اجرای سیستم ندارد. فقط یک فراخوانی محدود می‌سازد؛ ToolRegistry.execute() مرجع نهایی اعتبارسنجی، مجوز، گارد اجرا، اجرای Handler و ثبت نتیجه است. بنابراین تغییر وضعیت امنیتی بعد از ساخت Plan نیز باید در لحظه‌ی اجرا اثر کند.

**اجرای تست متمرکز:**

```powershell
python -m unittest discover -s tests -p "test_fast_commands.py" -v
```

**چک‌لیست پذیرش روی Windows:**
- فرمان خواندنی مثل «مشخصات سیستم چیه» باید بدون تماس با مدل و با نتیجه‌ی واقعی اجرا شود.
- فرمان قطعی مثل «صدا رو روی ۵۰ درصد بذار» باید فقط از Registry عبور کند و نتیجه‌ی واقعی ابزار گزارش شود.
- عبارت مبهم یا چندمرحله‌ای نباید Fast Path شود.
- خاموش‌کردن ابزارها یا فعال‌کردن Competitive Safe بین Plan و Run باید اجرای همان Plan را متوقف کند.
- یک فراخوانی یکسان در یک نوبت نباید دوباره Handler را اجرا کند.

وضعیت فعلی: تست‌های متمرکز و مرزهای اجرا در سورس اضافه شده‌اند، اما تا اجرای واقعی unittest و آزمون Windows، Fast Path از نظر runtime پذیرفته‌شده محسوب نمی‌شود. GitHub Actions نیز بخشی از معیار این مرحله نیست.

## ابزارها و سطح دسترسی
**سطح ۱ — فقط خواندن (با درخواست تو اجرا می‌شود)**
`get_datetime` (ساعت، تاریخ میلادی و شمسی، منطقه‌ی زمانی) · `get_system_info` (نسخه‌ی ویندوز، زبان، CPU، RAM، GPU) · `get_resource_usage` (CPU، RAM، GPU انویدیا، باتری) · `get_disks` · `get_network_info` · `list_running_apps` · `get_active_window` · `find_app` · `list_allowed_folders` · `search_files` · `list_folder` · `file_info` · `read_file` (متن/کد/CSV/JSON، DOCX، PDF)

**ابزارهای وب (سطح ۱، فقط‌خواندنی، با درخواست صریح)** — `web_search` · `web_read` · `web_research` · `web_research_status`؛ راهنمای کامل و امنیت: `docs/WEB_RESEARCH_FA.md`

**سطح ۲ — عملیات معمولی**
`open_app` (برنامه‌های Start Menu، بازی‌ها/برنامه‌های Steam، برنامه‌های نصب‌شده‌ی ویندوز، برنامه‌های Store و چند ابزار ثابت ویندوز؛ نمونه‌ی در حال اجرا را فعال می‌کند و گزارش واقعی می‌دهد — `docs/APP_LAUNCH_FA.md`) · `open_path` (فایل با برنامه‌ی پیش‌فرض یا پوشه در Explorer؛ برنامه/اسکریپت/میان‌بر را **هرگز** اجرا نمی‌کند) · `open_url` (فقط http/https)

**سطح ۳ — حساس (همیشه تأیید صریح)**
`delete_file` (فقط یک فایل، به سطل بازیافت؛ قابل برگشت) · `move_file` (بدون رونویسی). مدل این‌ها را اجرا نمی‌کند: Kira می‌گوید دقیقاً چه می‌شود و تو باید بنویسی «تأیید» (یا «لغو»). تأیید ۵ دقیقه اعتبار دارد و همان آرگومان‌های ذخیره‌شده را اجرا می‌کند؛ اگر پیام دیگری بفرستی، درخواست قبلی باطل می‌شود.

نصب/حذف برنامه، دستور مدیریتی، تغییر تنظیمات ویندوز و اجرای Shell در این نسخه **وجود ندارد**.

## دسترسی به فایل‌ها
- مجاز: Desktop، Documents، Downloads، Pictures، Videos، Music کاربر ویندوز (حتی اگر به درایو دیگر یا OneDrive منتقل شده باشند) و پوشه‌هایی که خودت اضافه کنی.
- همیشه ممنوع: پوشه‌ی اطلاعات خود Kira (تنظیمات، کلیدها، گفتگوها)، AppData، پوشه‌ی Windows و Program Files، پوشه‌های `.ssh` و مشابه، و فایل/پوشه‌ای که نامش شبیه رمز/کلید باشد (`.env`، `*.pem`، `password`، `رمز عبور` ...).
- مسیرها اول کامل resolve می‌شوند (لینک و `..` نمی‌توانند از محدوده بیرون بروند).
- کلیدها و توکن‌هایی که شبیه API Key باشند قبل از رسیدن به مدل پنهان می‌شوند.
- **توجه حریم خصوصی:** محتوای فایلی که از Kira می‌خواهی بخواند به مدلِ فعال می‌رسد؛ اگر مدل ابری است یعنی به همان سرویس فرستاده می‌شود. برای فایل‌های خصوصی از مدل محلی (Ollama) استفاده کن.

## تنظیمات (در `settings.json` کنار اطلاعات کاربر)
| کلید | پیش‌فرض | معنی |
|---|---|---|
| `tools_mode` | `auto` | `auto` فقط برای درخواست‌های مربوط به PC · `always` همیشه · `off` ابزارها خاموش و میان‌برهای ساده‌ی قدیمی (نوت‌پد، ماشین‌حساب...) |
| `tools_allowed_paths` | `[]` | پوشه‌های اضافه، مثل `["D:\\Projects"]` |
| `tools_max_rounds` | `4` | بیشترین مرحله‌ی ابزار در یک جواب (۱ تا ۶) |

## حافظه
نتیجه‌ی ابزارها در تاریخچه‌ی گفتگو یا حافظه‌ی دائمی Kira ذخیره **نمی‌شود**. فقط چند یادداشت کوتاه (مثل مسیر فایل‌های پیداشده) تا ۳۰ دقیقه در همین اجرای برنامه نگه داشته می‌شود تا بعداً مجبور نباشی همه‌چیز را از اول بگویی («همونی که پیدا کردی رو باز کن»)، و با بستن برنامه پاک می‌شود. فقط جواب نهایی Kira مثل همیشه در گفتگو ذخیره می‌شود.

## نمونه‌ها
- «ساعت چنده؟» → از ساعت ویندوز می‌خواند، برنامه‌ی Clock را باز نمی‌کند.
- «الان چقدر RAM مصرف شده؟» → مصرف و مقدار آزاد.
- «برنامه Discord رو باز کن» → در Start Menu پیدا می‌کند، اجرا می‌کند و گزارش واقعی می‌دهد. اگر نام مبهم باشد می‌پرسد.
- «فایل PDF مربوط به دیروز رو پیدا کن» → در پوشه‌های مجاز می‌گردد و فهرست می‌دهد.
- «این فایل رو پاک کن» → می‌پرسد؛ با «تأیید» به سطل بازیافت می‌رود.

## محدودیت‌های فعلی
- GPU: میزان استفاده فقط برای کارت‌های NVIDIA (با `nvidia-smi`)؛ برای بقیه فقط مدل کارت.
- «برنامه‌ای که دارم استفاده می‌کنم»: وقتی با Kira حرف می‌زنی پنجره‌ی خودش جلوست؛ پس بالاترین پنجره‌ی دیگر (به ترتیب پنجره‌ها) گزارش می‌شود و به‌عنوان حدس اعلام می‌شود.
- `open_app` برنامه‌های Start Menu، Steam، فهرست Installed apps ویندوز و Store را می‌بیند؛ برنامه‌های پورتابل بدون نصب ممکن است دیده نشوند. باز شدن را فقط از روی دیده شدن پنجره/پردازش گزارش می‌کند.
- جست‌وجوی فایل سقف زمان ۸ ثانیه و ۴۰هزار مورد دارد و در صورت ناقص ماندن اعلام می‌کند. PDFهای اسکن‌شده (بدون متن) خوانده نمی‌شوند. PDF به `pypdf` نیاز دارد.
- حذف فقط برای فایل (نه پوشه) است. کنترل کامل ویندوز، نصب/حذف برنامه، سیستم خودمختار پس‌زمینه و Game Mode عمداً پیاده نشده‌اند؛ معماری برای افزودنشان آماده است (ابزار جدید = یک تابع + یک خط ثبت در `kira/tools/builtin.py`).

## برای توسعه‌دهنده
`kira/tools/`: `registry.py` (تعریف/اعتبارسنجی/اجرا)، `access.py` (محدوده‌ی فایل)، `sysinfo.py`، `fileops.py`، `apps.py`، `builtin.py` (ثبت ابزارها)، `protocol.py` (پروتکل متنی و فیلتر Stream)، `agent.py` (حلقه‌ی ابزار روی HybridRouter). هر ابزار `json_schema()` دارد تا بعداً یک آداپتر Function Calling بومی اضافه شود.

## بلوتوث ویندوز (`bluetooth_status` · `bluetooth_on` · `bluetooth_off`)
- **روش:** API رسمی Windows Runtime (`Windows.Devices.Radios.Radio`: دسترسی، فهرست رادیوها، `SetStateAsync`) از طریق Windows PowerShell 5.1 با یک اسکریپت **ثابت**. هیچ متنی از کاربر/مدل وارد اسکریپت نمی‌شود؛ فقط یکی از سه حالت ثابت (خواندن / On / Off) انتخاب می‌شود. نیازی به نصب بسته‌ی اضافه نیست.
- **وضعیت‌ها:** روشن · خاموش · غیرفعال از سمت سیستم (حالت هواپیما/کلید سخت‌افزاری) · آداپتور شناسایی نشد · خطای دسترسی (`Let apps control radios` در Settings ← Privacy) · نامشخص (با علت خطا). وضعیت سرویس `bthserv` هم گزارش می‌شود.
- **تأیید واقعی:** بعد از روشن/خاموش‌کردن تا ۶ ثانیه دوباره وضعیت خوانده می‌شود. اگر به حالت خواسته نرسید، ابزار «ناموفق» برمی‌گرداند با وضعیت واقعی و علت؛ ادعای موفقیت نمی‌کند. اگر از قبل در همان حالت باشد، تغییری نمی‌دهد و همین را می‌گوید.
- **فقط با درخواست صریح:** ابزارهای تغییر وضعیت ورودی ندارند و فقط وقتی اجرا می‌شوند که پیام فعلی کاربر هم «بلوتوث» و هم «روشن/خاموش» را بگوید (در غیر این صورت رد می‌شوند، حتی اگر مدل بخواهد). پیام کوتاهِ «بکنش» بدون ذکر بلوتوث رد می‌شود.
- **محدودیت‌ها:** فقط ویندوز ۱۰/۱۱ با PowerShell 5.1 (`powershell.exe`)؛ حالت هواپیما/کلید سخت‌افزاری/غیرفعال بودن در Device Manager را نمی‌شود با این API برداشت. اتصال/جفت‌کردن دستگاه‌ها پیاده نشده است. روی ویندوز واقعی آزموده نشده است.
- **نمونه:** «بلوتوث رو روشن کن» · «بلوتوثم روشنه؟» · «بلوتوث رو خاموش کن».

## صدای ویندوز (Audio Manager)
ولوم، Mute، ولوم برنامه‌ها، فهرست و تغییر دستگاه‌های پیش‌فرض ورودی/خروجی با ابزارهای `audio_*`؛ تغییرها فقط با درخواست صریح در همان پیام اجرا و بعد از اجرا دوباره از ویندوز خوانده می‌شوند. راهنما: `docs/AUDIO_MANAGER_FA.md`.

> **دسترسی مرکزی (T5-Core):** سطوح READ / CONTROL / FILE / ELEVATED / PROTECTED، تأیید وابسته به همان عملیات و پارامترها، گارد درخواست صریح، ژورنال و Backendها در `docs/SYSTEM_ACCESS_FA.md` توضیح داده شده است.


### اصلاح تشخیص وظایف چندمرحله‌ای

تشخیص پیچیدگی در `planner.assess()` فقط یک پیش‌فیلتر سبک است و تصمیم/ساخت مراحل همچنان با مدل و اعتبارسنجی کد انجام می‌شود. شمارش فعل‌ها بر اساس تعداد وقوع است (نه تعداد ریشه‌های یکتا)؛ دو عمل متصل با «و / and» و فعل‌های رایج مانند «بگرد»، «بذار/بزار»، «انتخاب» و «اعمال» نیز به مسیر Planner هدایت می‌شوند. درخواست تک‌عملی و درخواست بدون دسته‌بندی ابزار همچنان ساده می‌ماند. تست‌های رگرسیون این مرزها در `tests/test_fast_commands.py` قرار دارند.


در اصلاح تکمیلی، صرف وجود دو واژهٔ شبیه فعل یا چند category برای ورود به Planner کافی نیست؛ باید نشانهٔ اتصال/ترتیب عملیات وجود داشته باشد. فعل‌های `create` و `make` و معادل‌های رایج فارسی ساخت نیز پوشش داده شده‌اند تا پرسش‌های توضیحی به‌اشتباه task تلقی نشوند.
