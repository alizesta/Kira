# Windows Control Layer — اعلام قابلیت‌های کنترل ویندوز

کدهای اصلی:
- kira/tools/wincontrol.py: تبدیل Capabilityهای اعلام‌شده به ابزارهای Registry.
- kira/tools/winmodules.py: ماژول‌های Apps، Bluetooth و Audio.
- kira/tools/desktop.py: ماژول تعامل دسکتاپ (پنجره، صفحه‌کلید، ماوس، Clipboard و UI Automation).
- kira/tools/winrunner.py: اجرای PowerShell ثابت و محدود.
- kira/tools/sysaccess.py: مدیر مرکزی مجوز، تأیید، backend و ژورنال عملیات.

## جایگاه در معماری

WindowsControlLayer دیگر مالک مستقل مجوزها یا ژورنال نیست؛ فقط قابلیت‌ها را با نام، handler، پارامترهای بسته، سطح ریسک، شرط نیت و Backend اعلام می‌کند. تمام اجراها از ToolRegistry.execute() عبور می‌کنند و سیاست مرکزی در System Access Manager اعمال می‌شود.

ماژول‌های Windows که در kira/tools/builtin.py فعلاً ثبت شده‌اند:
- **Apps:** پیدا کردن و بازکردن برنامه‌های نصب‌شده و بازی‌های Steam.
- **Bluetooth:** خواندن وضعیت و روشن/خاموش‌کردن با درخواست صریح کاربر.
- **Audio:** خواندن و تغییر وضعیت/بلندی صدای سیستم و برنامه‌ها، دستگاه‌های ورودی و خروجی.
- **Desktop:** فهرست/تمرکز/بستن/تغییر وضعیت پنجره‌ها، تایپ و کلیدهای مجاز، کلیک محدود روی کنترل‌های UI، و Clipboard با محدودیت‌های امنیتی.

نام دامنه‌های دیگری مانند wallpaper، tray و system در جدول دامنه‌ها تعریف شده‌اند، اما وجود نام دامنه به معنی ثبت و فعال‌بودن ماژول آن نیست.

## سطوح دسترسی مرکزی

| سطح | کاربرد | کنترل |
|---|---|---|
| READ | خواندن اطلاعات | بدون تأیید |
| CONTROL | کنترل برگشت‌پذیر ویندوز و برنامه‌ها | درخواست صریح در پیام فعلی یا دلیل opt-out ثبت‌شده |
| FILE | عملیات غیرمخرب فایل | مسیرها باید از PathPolicy عبور کنند |
| ELEVATED | عملیات نیازمند سطح Administrator | تأیید صریح؛ قابلیت UAC عمومی در این نسخه اعلام نشده است |
| PROTECTED | عملیات حساس، مخرب یا پرریسک | تأیید صریح برای همان ابزار و همان آرگومان‌ها |

### قواعدی که در کد اجرا می‌شوند

1. مدل فقط درخواست ابزار می‌دهد؛ خودش مجوز صادر نمی‌کند.
2. ابزارهای CONTROL/FILE که نیازمند نیت صریح‌اند، باید با متن پیام فعلی کاربر تطبیق داشته باشند.
3. پس از خواندن محتوای بیرونی (وب، فایل، MCP یا نتیجه ایجنت)، داده به‌عنوان tainted علامت‌گذاری می‌شود؛ بعضی عملیات بعدی نیازمند تأیید می‌شوند تا دستور پنهان داخل محتوا اجرا نشود.
4. تأیید PROTECTED به عملیات و آرگومان‌های ذخیره‌شده متصل است، یک‌بارمصرف است و زمان اعتبار محدودی دارد. پیام جدیدی که عملیات دیگری را درخواست کند، تأیید قبلی محسوب نمی‌شود.
5. نتیجه باید از handler واقعی بیاید؛ مدل نباید از صرف درخواست ابزار نتیجه موفقیت بگیرد.
6. هر عملیات از سیاست مرکزی و ژورنال System Access عبور می‌کند. این ژورنال با OperationLog قدیمی WindowsControlLayer یکی نیست.

## اجرای PowerShell

PowerShell آزاد یا اجرای دستور دلخواه از متن مدل وجود ندارد. در صورت نیاز، فقط FixedScript ثابتِ تعریف‌شده در کد از طریق winrunner.run_fixed اجرا می‌شود؛ داده‌های متغیر به‌عنوان ورودی جداگانه منتقل می‌شوند، نه اینکه در متن اسکریپت ساخته شوند. نام پارامترهای شبیه command، script، shell و powershell در تعریف Capability رد می‌شوند.

## ارتباط با ابزارهای دیگر

- عملیات فایل در kira/tools/fileops.py و fileagent.py تعریف می‌شوند و از PathPolicy و Registry استفاده می‌کنند.
- ابزارهای وب و WebIntel از همان Registry استفاده می‌کنند؛ خواندن وب، اجرای فایل یا اسکریپت را مجاز نمی‌کند.
- ابزارهای MCP از kira/mcp/hub.py به Registry اضافه می‌شوند؛ annotation سرور MCP مجوز را تعیین نمی‌کند.
- سیاست کامل و جزئیات taint/confirmation در docs/SYSTEM_ACCESS_FA.md آمده است.

## محدودیت و وضعیت آزمون

وجود تست‌های واحد و قراردادهای ایستا به معنی آزمون روی Windows واقعی نیست. تعامل با پنجره‌ها، UI Automation، Clipboard، بلوتوث و دستگاه‌های صوتی باید روی Windows واقعی و با سخت‌افزار/برنامه‌های هدف بررسی شود.
