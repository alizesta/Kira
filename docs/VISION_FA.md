# بینایی بازی در Kira

## رفتار

Vision فقط بعد از فعال‌سازی دستی Game Mode و انتخاب Story Mode اجازه‌ی دریافت و تحلیل فریم دارد. Competitive Safe همچنان هیچ تصویری از بازی نمی‌گیرد.

سه حالت در منوی 🎮 وجود دارد:

| حالت | فاصله‌ی تحلیل | اندازه‌ی هدف | کیفیت JPEG |
|---|---:|---:|---:|
| اقتصادی | ۵ ثانیه | حداکثر 854×480 | 62 |
| هوشمند | ۱ ثانیه | حداکثر 960×540 | 66 |
| سریع | نیم‌ثانیه | حداکثر 1280×720 | 70 |

حالت اقتصادی پیش‌فرض است. فاصله‌ی بالا نرخ **درخواست تحلیل مدل** است، نه FPS ضبط تصویر؛ همه‌ی فریم‌های نمایشگر به مدل فرستاده نمی‌شوند.

## مسیر پردازش

1. GameModeMonitor فقط پنجره‌ی بازی را می‌گیرد و تصویر را در اندازه‌ی محدودشده نگه می‌دارد.
2. FrameGate نرخ تحلیل را محدود و فریم‌های تکراری را حذف می‌کند.
3. تصویر به JPEG تبدیل می‌شود و از مسیر attachment فعلی Kira عبور می‌کند.
4. VisionAnalysisWorker تحلیل را خارج از رشته‌ی رابط کاربری و از طریق HybridRouter اجرا می‌کند.
5. اگر تحلیل قبلی هنوز در حال اجرا باشد، فریم تازه برای آن درخواست انباشته نمی‌شود؛ چرخه‌ی بعدی تصویر جدید را می‌گیرد.
6. نتیجه فقط وقتی Game Mode و مجوز Vision هنوز فعال باشند وارد گفتگو می‌شود.

## سازگاری مدل

تحلیل تصویر به مدلی نیاز دارد که ورودی تصویر (multimodal / vision) را پشتیبانی کند. HybridRouter تصویر را به قالب استاندارد ضمیمه می‌کند؛ مدل متنیِ صرف نمی‌تواند محتوای تصویر را تحلیل کند و خطای provider به شکل پیام قابل‌فهم نمایش داده می‌شود. پشتیبانی واقعی مدل نصب‌شده‌ی Ollama باید در اجرای عملی تأیید شود؛ نام مدل به‌تنهایی تضمین‌کننده‌ی Vision نیست.

## منابع و ایمنی

- پردازش تصویر و درخواست مدل در رشته‌ی پس‌زمینه انجام می‌شود.
- در هر لحظه حداکثر یک تحلیل Vision فعال است.
- هیچ ویدیویی ذخیره یا به‌صورت پیوسته آپلود نمی‌شود؛ فقط فریم‌های نمونه‌برداری‌شده برای تحلیل فرستاده می‌شوند.
- حالت Competitive Safe، محدودیت‌های دسترسی بازی و کنترل سیستم را تغییر نمی‌دهد.
- OCR جداگانه یا وابستگی سنگین OCR اضافه نشده؛ خواندن نوشته‌های قابل‌مشاهده به مدل Vision واگذار شده است.
- آمار شمارنده‌ها و تأخیر آخرین تحلیل در FrameGate نگهداری می‌شوند.


## تکمیل مسیر مدل و لغو امن
- تحلیل خودکار تصویر فقط از Routeای استفاده می‌کند که نام مدل آن به‌صورت شناخته‌شده Vision باشد یا تنظیم Provider آن `vision_enabled: true` داشته باشد. مدل‌های ناشناخته عمداً برای تصویر انتخاب نمی‌شوند.
- برای Provider سفارشی OpenAI-compatible، مقدار `vision_enabled` را فقط وقتی فعال کنید که مدل واقعاً ورودی تصویر را پشتیبانی می‌کند.
- تشخیص قابلیت Ollama برای هر آدرس سرور و نام مدل جداگانه cache می‌شود؛ خطای موقت یا خاموش‌بودن سرور به‌عنوان ناتوانی دائمی مدل cache نمی‌شود و مدل‌های embedding نیز به‌اشتباه Vision شناخته نمی‌شوند.
- با خاموش‌کردن Game Mode یا خروج واقعی از برنامه، درخواست فعال Vision لغو و اتصال HTTP آن بسته می‌شود.
- آخرین فریم بازی هنگام ارسال پیام عادی در Story Mode همچنان به‌عنوان ضمیمه‌ی همان سؤال ارسال می‌شود.
- OCR محلی اختیاری است: اگر Pillow و pytesseract از قبل نصب باشند اجرا می‌شود؛ در غیر این صورت بدون خطا رد می‌شود و مدل Vision همچنان تصویر را تحلیل می‌کند. هیچ بسته‌ای خودکار دانلود یا نصب نمی‌شود.
- OCR محلی اندازه‌ی ورودی را محدود می‌کند، تصاویر بیش از ۴۰ مگاپیکسل را رد می‌کند و اجرای Tesseract حداکثر ۴ ثانیه مهلت دارد.
- تغییر پروفایل از Story به Competitive Safe نیز فوراً Capture را متوقف می‌کند و تحلیل Vision در حال اجرا را لغو می‌کند؛ فقط مخفی‌کردن نتیجه کافی نیست، چون تصویر نباید پس از لغو مجوز همچنان ارسال شود.
- ورود به Competitive Safe علاوه بر لغو Vision، مجوزهای معلق را باطل و کارهای محلی/Agent و فرمان در حال اجرای Ai1 Code را متوقف می‌کند.
- میانبرهای ثابت دسکتاپ و بازکردن مرورگر نیز در این پروفایل مسدودند؛ خاموش‌بودن Tools mode دیگر راه دورزدن محدودیت نیست.
- توقف Ai1 Code در Context همان Session انجام می‌شود تا اگر تب دیگری فعال است، وضعیت Busy یا صف پیام آن تب تغییر نکند.
- با لغو مجوز Capture، زمان‌بندی و اثرانگشت فریم قبلی نیز reset می‌شوند تا فعال‌سازی دوباره با تأخیر نمونه‌برداری قبلی یا حذف نتیجه‌ی تکراری شروع نشود.
- با خروج پنجره‌ی بازی از پیش‌زمینه، هدف Capture قبلی پاک می‌شود؛ خاموش‌کردن Game Mode نیز پنجره‌ی ذخیره‌شده را پاک می‌کند تا فریم یک بازی قدیمی دوباره گرفته نشود.
- پیش از هر نمونه‌برداری، پنجره‌ی پیش‌زمینه دوباره بررسی می‌شود؛ تایمر تشخیص بازی به‌تنهایی برای جلوگیری از Capture پنجره‌ی پس‌زمینه کافی نیست.
- تحلیل خودکار پس‌زمینه از مسیر streaming استفاده می‌کند تا Stop و تغییر پروفایل بتوانند اتصال HTTP فعال را قطع کنند؛ درخواست لغوشده نتیجه‌ی ناقص را وارد چت نمی‌کند.
- Worker لغو را به‌صورت Event مستقل به Router می‌دهد؛ اگر لغو هنگام تشخیص مدل یا پیش از شروع اتصال رخ دهد، درخواست جدید اصلاً به Provider ارسال نمی‌شود.
- Router در آغاز، پیش از ساخت Provider و هنگام خواندن جریان، Event لغو را بررسی می‌کند؛ بنابراین Event لغوشده با پاک‌کردن داخلی Stop دوباره فعال نمی‌شود.
- بدنه‌ی آپلود تصویر نیز در هر قطعه Event لغو را بررسی می‌کند؛ لغو حین ارسال فایل، خواندن قطعات بعدی تصویر را متوقف می‌کند.
- تصویر ضمیمه‌شده به پیام عادی، پس از تعیین نقش پردازش، Route بینایی را انتخاب می‌کند؛ Scope انتخاب Vision درون Scope نقش قرار می‌گیرد تا ترجیح مدل بینایی بازنویسی نشود.
- نتیجه‌ی تحلیل پس‌زمینه به Session شخصیتی که Capture را آغاز کرده تحویل داده می‌شود؛ اگر هنگام تحلیل تب دیگری باز شود، پاسخ اشتباهاً وارد گفت‌وگوی آن شخصیت نمی‌شود. پیام جدید همان Session نیز تا پایان لغو Vision در صف می‌ماند.
- تحویل نتیجه و تخلیه‌ی صف با SessionRelay انجام می‌شود تا سیگنال‌های Thread پس‌زمینه به تب درست برسند و پس از بسته‌شدن پنجره پیام جدیدی شروع نشود.
- ارسال پیام‌های صف‌شده پس از بسته‌شدن پنجره نیز Guard دارد؛ callback دیررس نمی‌تواند Thread یا درخواست تازه‌ای بعد از Shutdown بسازد.
- اگر کاربر هنگام تحلیل پس‌زمینه پیام بفرستد، تحلیل لغو و پیام به صف همان Session منتقل می‌شود؛ پرچم ورودی صوتی نیز همراه پیام در صف حفظ می‌شود.
- تست‌های مستقل برای انتخاب Route، لغو هنگام تغییر پروفایل، محدودیت نرخ فریم، حذف فریم تکراری، صف تک‌فریمی و مسیر خطای OCR وجود دارند.
